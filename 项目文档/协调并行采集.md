# 协调并行采集

本轮范围仍是冻结审核的 220 页、4161 个待采编号，不扩展编号或重试已隔离失败。

入口：`.runtime/collect_retry_220_parallel.py`。它读取原队列并续跑未完成批次，每批最多20个不同编号。运行中由协调器单独写队列，采集子进程各用独立检查点和临时数据库。校验、疑似重复来源隔离及验收库导入沿用原脚本，全部由主线程串行调度。

并发上限2。可用物理内存低于768MiB时不再派发第二个worker；已有worker先完成。没有内存读数时只用1个。不是按总内存盲目开启更多进程：本次实测全局请求间隔10秒构成主要瓶颈，多于2个进程通常只会排队。

所有详情worker共享 `pacing.json` 和OS锁，至少相隔10秒发起请求，并采用所观察到的更严格robots间隔。锁跨连接头阶段持有，网络正文读取可重叠。限流等待不计入原30秒网络I/O预算，网络超时、响应上限、来源/类型检查、30/60秒重试和不跟随重定向规则不变。401/403/429或重定向触发全局停止标记；其他校验/入库错误停止协调器。停止标记需人工核查，不自动删除重启。

队列 `concurrency` 字段记录实际并发、可用内存；`coordinator_script` 标识当前入口。`pacing.json`最多保留128次跨进程实际发起时间，用于核对全局间隔。采集请求记录的 observed_at_utc 在限速排队前生成，不能据此推算真正发起间隔。

原队列路径不变。日志为冻结审核目录中的 `parallel.stdout.log`、`parallel.stderr.log`，`worker.pid`为实际协调进程。批次日志及 `approved/preview_import.json` 路径不变。监控需遍历所有尚未完成的批次，不能只看最后一批。封面worker仍通过原队列跟随，不需要重启。

交接备份：`.runtime/directory_detail_queues/retry_220_20261020/handoff_20261020_174828/`。旧协调器在未有在途请求的已保存检查点停止，保留第62批所有已完成项；交接时本轮已入库1219部。

离线验证覆盖：共享全局间隔、严格robots间隔保持、限制响应阻止其他worker继续请求、损坏限速文件停止、内存阈值、两个采集任务编号不重叠、单线程串行入库、原进度保留，以及原采集器断点/重试/哈希检查回归。
