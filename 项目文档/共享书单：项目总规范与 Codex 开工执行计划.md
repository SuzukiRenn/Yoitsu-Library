## 0. 项目总览

「共享书单」是供现有轻小说交流群使用的匿名书单网站。群友持有链接即可访问，不需要注册普通用户账号。网站帮助群友提交作品、分享推荐理由、通过公共「+1」表达"我也推荐"，并使用标准标签发现作品；同时支持每月开展独立统计的集中分享活动。

项目以文库8作为主要书目资料和标准标签来源。用户输入作品名称时，系统优先通过本地书目数据库、标准书名、已确认别名和模糊匹配找到作品；仅在错字、缺字或其他差异导致本地匹配失败时，才使用
DeepSeek
辅助匹配。即使无法匹配文库8，用户仍然可以提交作品，不因缺少封面或标签而被阻止。

网站实际编码和搭建由 Codex
执行；本项目的协作方式是先讨论并确认产品规则，再将本文件作为统一开发依据。

### 0.1 MVP V1 目标

首版必须形成完整闭环：

1.  导入并查询文库8作品元数据及标准标签。
2.  用户输入书名时获得候选补全，能选择已有作品，也能直接提交未匹配作品。
3.  已确认指向同一作品的推荐只展示一个正式作品；未匹配作品的身份边界见 §4.6，不承诺仅凭书名消除所有现实作品重复。
4.  不同匿名用户可以分别提交各自的推荐理由。
5.  公共「+1」独立于推荐理由，用户可添加或取消。
6.  标签来自文库8标准标签库，用户不能自由创建标签。
7.  支持月度活动、活动推荐、活动点赞、活动时间管理和往期活动。
8.  管理员可以纠错、隐藏作品、管理标签、管理活动和处理重复作品。
9.  重复作品合并时保护关联数据、历史快照和审计记录，并支持有条件的安全撤销。
10. 关键操作具备数据库约束、事务保护、基本安全防护和验收测试。

### 0.2 首版暂不追求

以下项目可以后续迭代，不应阻塞首版上线：

-   复杂的管理员角色与权限等级系统。
-   高级统计报表和复杂数据分析。
-   大量批量管理工具。
-   复杂推荐算法、个性化推荐和社交关系。
-   页面动画、复杂视觉效果及非必要微交互。
-   小说正文抓取、下载或阅读功能。

## 1. 项目定义与产品原则

### 1.1 名称与定位【已确认】

-   网站名称固定为 **「共享书单」**，不在名称中加入"轻小说"或"推荐墙"。
-   主要用户是现有轻小说交流群成员。
-   当前以轻小说分享为主，但名称和基础架构不永久限定只能收录轻小说。
-   核心价值是集中收集群友推荐、避免重复提交、展示推荐理由、提供「+1」和标准标签筛选。

### 1.2 普通用户访问方式【已确认】

-   普通群友持有网站链接即可访问。
-   不要求注册普通用户账号，不要求填写昵称、QQ 号或真实身份信息。
-   推荐理由和其他贡献在前台匿名展示，不建立公开匿名昵称系统。
-   匿名令牌只用于后台识别同一浏览器的操作归属，不代表实名身份，也无法保证一个现实中的人只能操作一次。
-   用户清除
    Cookie、更换浏览器或设备后，可能获得新的匿名身份。旧数据继续保留，但用户可能无法再管理旧身份提交的记录。

### 1.3 数据设计原则【已确认】

-   作品资料、推荐理由、点赞、标签关联、活动记录和管理员审计分开保存。
-   一部已确认身份的作品应有一个正式的本地作品记录。
-   不能仅凭书名相似、作者相同、译名相近或 AI 判断自动合并作品。
-   隐藏、撤回、取消、归档和合并不应导致无关数据丢失。
-   用户只能管理自己有权管理的关联记录。
-   标准标签定义与某部作品的标签关联是两回事；撤销一条关联不等于删除标准标签。
-   历史活动和合并历史必须可追溯。
-   统计应根据有效记录计算，不依赖容易失真的手动计数器。

## 2. 作品库、公共书单与推荐理由

### 2.1 作品库与公共书单的区别【已确认】

-   `works`
    保存文库8预先采集的作品，以及群友提交但暂时无法匹配文库8的作品。
-   文库8作品进入本地书目库，不等于自动出现在公共书单。
-   用户提交推荐后，作品进入公共书单。
-   月度活动推荐也会使作品进入公共书单。
-   公共书单和月度活动可以共用作品资料，但推荐理由、点赞和统计分别保存。
-   指向同一正式作品的推荐在公共书单中只展示一次，即使有很多群友推荐它；身份尚未确认的重复候选按 §4.6 处理。

建议用 `works.public_added_at`
记录作品首次进入公共书单的时间。作品记录不能因为一条推荐被撤回或清空而被删除。

即使最后一条公共推荐理由被清空，作品仍保留在公共书单；不因零贡献自动退出。公开可见性继续遵守隐藏与合并规则。

上述收录和活动推荐同时遵守 §4.6：与隐藏作品仅同名、身份未知的提交先待核查，核查前不公开、不计活动推荐；允许提交不等于立即获得公开资格。

### 2.2 公共推荐理由【已确认】

-   不同匿名浏览器可以分别为同一作品留下自己的公共推荐理由。
-   同一匿名身份对同一作品最多有一条有效的公共推荐理由记录。
-   推荐理由选填；没有理由也可以提交作品。
-   公共理由为空时只完成作品收录，不创建空公共推荐记录；公共有效理由数不等同于所有曾推荐过该作品的人数。
-   推荐理由为纯文本，不支持 Markdown、HTML 或富文本。
-   每条理由最多 200 个 Unicode 码点，统一换行并去除首尾空白后校验；输入框按同一口径实时计数，超过限制禁止提交，不自动截断。组合表情可能包含多个码点，完整输入协议见 §7.5。
-   前端和服务端都必须校验长度。
-   用户只能修改或清空自己的公共推荐理由。
-   修改自己的公共理由不影响其他用户的理由，也不影响月度活动中的理由。
-   清空公共推荐理由按已讨论规则删除该匿名身份对应的公共推荐记录；不删除作品记录，也不影响其他用户的记录、公共「+1」或活动记录。
-   前台不显示推荐理由作者身份，不显示空白理由。

**实现注意：**
公共书单收录状态与某一条理由记录应分开管理。删除一条公共推荐记录不得级联删除作品。公共书单列表的最终可见性还应遵守作品是否被管理员隐藏、是否已经合并等规则。

### 2.3 月度活动推荐自动进入公共书单【已确认】

-   用户提交活动推荐时，系统在同一事务内确保该作品进入公共书单。
-   提供默认不勾选的“同时作为公共理由”选项；只有用户主动勾选、该匿名身份当前无有效公共理由且本次活动理由非空时，才创建公共理由。复制与活动提交在同一事务内完成。
-   如果该匿名身份已经有公共推荐理由，保留原公共理由，不用活动理由覆盖。
-   用户曾清空公共理由后，后续活动推荐仍须再次主动勾选且满足上述条件，才重建公共理由；不自动恢复旧理由。
-   活动理由和公共理由之后分别修改、分别保存。
-   活动推荐不自动产生公共「+1」，也不自动产生本期活动点赞。
-   活动理由为空时，活动推荐仍然有效；不展示空白理由。

公共空理由不创建公共推荐记录；最后一条公共理由清空后作品仍留在公共书单，遵守隐藏与合并规则。活动空理由始终保留有效活动推荐，不因没有文本而减少推荐人数。

### 2.4 公共列表排序与筛选【已确认】

-   按有效公共「+1」数降序、首次公共收录时间降序、正式作品 ID 升序排序；不套用活动排序。
-   多标签筛选采用 AND，即作品须同时满足全部所选标签。
-   分页和标签计数只包含公开可见的正式作品；排除隐藏、待核查及被合并的非正式记录，按正式作品 ID 去重；标签关联还须遵守 §5.4 的停用与禁止规则。
-   标签筛选区的标签排序仍按 §5.3，不与作品排序混用。

## 3. 公共「+1」规则

### 3.1 「+1」的含义【已确认】

-   「+1」表示"我也推荐这本书"或中文互联网常用的"同样"。
-   它是轻量支持操作，不是新增推荐理由，也不是创建新作品。
-   同一匿名身份对同一作品只能有一个有效公共「+1」。
-   用户可以取消自己的公共「+1」，之后可以再次添加。
-   公共「+1」与公共推荐理由独立；同一用户可以同时拥有两者。
-   公共「+1」只用于已进入公共书单的作品。只存在于文库8书目库、尚未进入公共书单的作品，应先通过推荐进入公共书单。
-   公共「+1」与月度活动点赞完全独立，不互相增加、不互相取消。

### 3.2 统计规则【已确认】

-   统计有效点赞记录，不把已取消的点赞计入总数。
-   同一匿名身份重复点击不能造成重复计数。
-   数据库唯一约束必须防止并发请求产生重复有效点赞。
-   取消点赞只影响对应范围内的点赞，不删除推荐理由或作品。

## 4. 文库8数据采集与作品匹配

### 4.1 计划采集的元数据【已确认】

仅采集共享书单需要的作品元数据，字段以文库8实际可获得的内容为准：

-   文库8作品 ID、标准书名、作者、详情页地址。
-   标签及标签原始 ID（如果可获得）。
-   简介、封面地址（如果可获得）。
-   分类、作品状态、字数、来源更新时间等可用字段。

**不抓取小说正文、章节内容或整本电子书。**

文库8匹配失败时，封面可以为空，前端使用统一的默认占位图。缺少封面不是阻止提交的理由。

### 4.2 已完成的文库8技术验证

-   已使用用户授权的 Chrome 环境完成少量真实搜索测试。
-   已验证搜索可能直接进入作品详情页，也可能返回多个候选。
-   已验证可以通过作品编号选择候选，并从详情页获取书名、作者、标签、简介、封面地址等资料。
-   已验证详情页作品编号可以与所选编号做一致性校验。
-   已完成命令行原型和离线测试。
-   **尚未执行文库8全站批量采集。**
-   服务器能否独立访问、批量采集的请求节奏、增量更新方式和封面本地存储方式仍需技术验证。
-   既有容量估算只是规划估算，不代表已经测量全站数据量。

本地证据：`tests/wenku8_browser/online_search_20261018/test_report.md`、`tests/wenku8_browser/selected_detail_20261018/test_report.md`、`tests/wenku8_browser/logging_online_review_20261018/test_report.md`。以上是历史小样本证据，不代表当前线上状态或全站兼容性。本次文档修订未新增在线验证。

**数据质量要求：** 已有报告发现搜索列表长标题可能截断。列表可见标题仅用于候选展示，未经详情核实不得作为正式来源标准书名。保存字段获取状态，区分有效值、来源明确为空、未获取和解析失败；单条必需身份字段校验失败时隔离该条，不使整批失败，也不得伪装为成功导入。

### 4.3 作品输入与候选匹配流程【已确认】

1.  用户输入书名。
2.  系统优先查询本地作品库中的标准书名和已确认别名。
3.  输入时提供候选补全或下拉列表，尽量展示书名、作者、封面（如有）及是否已经进入公共书单。
4.  本地精确匹配失败时，使用本地规范化和模糊匹配寻找候选。
5.  如果候选明确，用户自行选择；选择后关联现有作品，不新建重复作品。
6.  本地匹配仍失败或无法可靠判断时，才调用 DeepSeek 辅助匹配。
7.  DeepSeek 返回的候选必须由用户确认；AI
    不能单方面确认作品身份，也不能自动合并作品。
8.  仍无法匹配时，允许用户按原始书名直接提交；仅与隐藏作品同名而身份未知时，按 §4.6 进入待核查，不直接公开。
9.  创建新作品前再次查重，防止候选搜索与最终提交之间出现重复。

### 4.4 DeepSeek 的职责边界【已确认】

-   DeepSeek **不负责生成或补充标签**。
-   匹配文库8成功后，直接使用文库8标签；用户也可以选择标准标签库中已有的其他标签。
-   匹配失败的作品可进入公共书单，不要求 DeepSeek 补标签；与隐藏作品仅同名而身份未知的提交先按 §4.6 待核查，核查前不公开、不计活动推荐。
-   DeepSeek
    的用途是：当用户输入的书名存在错字、缺字、别名差异等问题，导致本地作品库无法匹配时，辅助搜索可能对应的已收录作品。
-   AI 只能给候选，用户确认后才建立关联。
-   不因 AI 判断相似就自动合并作品。

**技术限制：** 不能假设普通 DeepSeek API 一定自带联网搜索。Codex
必须先核实实际使用的 API /
模型是否具备联网检索能力。如果没有，则以本地作品库为检索范围，让模型辅助纠错和候选排序；若确需外部搜索，应单独验证可用接口和成本。

### 4.5 文库8数据更新与管理员覆盖【已确认】

每个元数据字段独立管理来源同步和管理员手动覆盖。

建议字段：

-   `original_submitted_title`：最初提交的书名，保留原始输入。
-   `wenku8_title`、`wenku8_author`、`wenku8_description`、`wenku8_cover_url`：文库8来源值。
-   `title_override`、`author_override`、`description_override`、`cover_url_override`：管理员手动覆盖值。
-   可选的
    `wenku8_detail_url`、分类、作品状态、字数、来源更新时间等字段。

显示优先级：

1.  对应字段存在管理员覆盖值时，显示覆盖值。
2.  否则显示文库8来源值。
3.  书名在尚未匹配文库8且无覆盖值时，使用最初提交的书名。
4.  作者、简介或封面没有来源值时允许为空，不凭空生成内容。

-   文库8更新时同步来源字段，不覆盖管理员手动覆盖值。
-   管理员可逐字段恢复文库8同步；恢复操作清除该字段覆盖值，不影响其他字段。
-   管理员覆盖与恢复操作记录在 `admin_audit_logs`。
-   原始提交书名不因文库8匹配成功或书名更新而改变。
-   原始提交书名不自动成为别名；只有经过确认或管理员明确添加的别名才进入别名库。

**空值与同步修订要求：**

-   获取失败或未获取的字段不得覆盖已有来源值；完整页面明确提供空值时，才可按字段规则清空来源值。
-   管理员覆盖必须区分“无覆盖”和“主动覆盖为空”，不能仅用真假值判断。作者、简介、封面可主动清空；最终显示书名不得为空。
-   恢复同步是取消覆盖状态，与主动清空不同。字段级覆盖标记或等效结构在阶段 1 落实。
-   纯导入作品的 `original_submitted_title` 可为空；用户创建未匹配作品时必填。后续推荐输入不覆盖最初输入，合并时保留各原记录供追溯。

### 4.6 作品身份与请求去重【修订要求】

-   已确认的本地作品 ID、可信来源 ID 是关联依据；同名、相似名或同作者只能产生候选，不能证明同一作品。
-   未匹配作品允许暂时存在疑似重复，由管理员核查；创建前再次查重仍需执行，但不得据此承诺消除所有未知身份重复。
-   同一次提交的网络重试必须幂等，避免重复创建作品及关联。幂等键绑定服务端识别的匿名身份、操作范围和请求内容；同键不同内容拒绝。保存期限与重试响应在阶段 1 的接口规范中定义。
-   已有未匹配作品后来确认文库8身份时，若该来源 ID 已被其他作品占用，不先写入冲突 ID，不自动迁移已有贡献；进入管理员合并预览。用户选择已有候选只决定当前提交归属，不授权合并历史记录。
-   隐藏检查应覆盖候选、详情、读写接口及合并目标。已确认指向隐藏作品的提交拒绝公开写入，不能新建替身绕过隐藏。
-   仅与隐藏作品书名相同、身份未知时，允许提交但进入管理员待核查状态；核查前不公开、不计活动推荐，并明确提示提交者。这是未匹配作品可直接公开的例外，不得按同名直接认定同作或自动合并。待核查不能绕过活动截止、普通用户写入权限或隐藏检查。

## 5. 标准标签库

### 5.1 标签来源与使用规则【已确认】

-   文库8标签是标准标签库的唯一来源。
-   不允许群友自由创建标签。
-   不提供"提交新增标签建议"功能。
-   群友只能从现有标准标签中选择。
-   文库8匹配成功的作品直接使用文库8提供的标签。
-   群友可以为作品增加标准标签库中已经存在的其他标签。
-   文库8匹配失败的作品仍可进入公共书单，隐藏同名身份未知的例外按 §4.6 待核查；用户可以选择已有可用标准标签，也可以暂时不添加标签。
-   后续采集到文库8新增的标签时，可以将其纳入标准标签库。

### 5.2 标签身份与疑似重复【已确认】

-   如果文库8提供稳定标签 ID，优先用原始 ID 识别标签。
-   两个标签原始 ID 不同，即使显示名称完全相同，也先保留独立记录。
-   系统可以标记名称完全相同或高度可疑的标签，供管理员核查。
-   不自动合并仅仅名称相似的标签。
-   管理员确认重复后可以执行专门的标签合并/纠错操作；具体迁移细节由后台管理功能落实，并保留审计记录。
-   如果文库8没有提供标签
    ID，则使用规范化名称辅助去重与排查，但不能仅凭语义相似自动合并。

### 5.3 标签关联与权限【已确认】

-   标签属于作品，不属于某一条推荐理由。
-   同一作品同一标签在页面上只展示一次。
-   数据库仍分别保留文库8来源、不同匿名用户来源和管理员处理来源的关联记录。
-   普通用户可以撤销自己添加的标签关联。
-   普通用户不能撤销文库8来源的标签关联，也不能撤销其他用户的关联。
-   管理员可以纠正错误或不当关联。
-   移除一条关联不等于删除标准标签定义。
-   标签筛选区按该标签关联的公共书单作品数量降序排列；数量相同时按标签名称排序。

### 5.4 标签同步与纠错持久性【修订要求】

-   区分来源撤销、用户撤销、管理员移除和合并归档；单一 `removed_at` 不足以表达这些原因，阶段 1 必须补充状态或等效模型。
-   完整且成功的来源标签集合才能用于判定来源关联撤销；标签解析失败或不完整时保留旧关联，不能把空数组当作来源清空。
-   管理员移除来源关联必须保留纠错标记，后续导入不能自动恢复该关联；由管理员明确恢复后才重新跟随来源。
-   标签合并保留原始来源身份到主标签的映射，后续导入先解析映射，避免重新生成已合并标签。无来源 ID 时保留经确认的来源名称映射；语义相似仍不能自动归并。
-   标签合并、来源映射、关联去重和审计在同一事务中完成，保留来源与操作者；禁止映射循环。它与作品合并是不同操作，不默认承诺标签合并也支持自动撤销。
-   标签停用后停止新选择和公开展示，保留已有来源关联历史；不能仅因停用删除标签或关联。
-   单条来源纠错只抑制该来源关联，不代表禁用其他来源。管理员如需禁止某作品上的某标签全部来源，使用独立的作品级禁止标记；用户添加及来源导入均不能绕过该标记，历史关联保留。
-   标签公开展示与筛选须遵守停用及作品级禁止；标签计数仅包含当前公开可见作品，并按正式作品 ID 去重。

## 6. 月度活动完整规则

### 6.1 活动状态【已确认】

活动状态包括：

-   **草稿：** 尚未正式安排。
-   **待开始：** 已安排，等待计划开始时间。
-   **进行中：**
    允许普通用户提交活动推荐、修改自己的活动理由、点赞或取消点赞。
-   **暂停：** 普通用户只读；活动倒计时继续。
-   **已结束：** 普通用户永久只读，不可重新开放；允许有审计的管理员纠错、合并/撤销和隐藏/恢复，往期统计按修正后有效记录重算并提示“已修正”，见 §6.10。
-   **已取消：** 活动尚未开始时由管理员取消，永久不可重新启动。

### 6.2 状态转换与时间规则【已确认】

-   到达计划开始时间后，系统自动开始活动并记录 `started_at`。
-   管理员可以提前手动开始；此时以实际操作时间记录 `started_at`。
-   到达当前有效截止时间后，系统自动结束活动并记录 `ended_at`。
-   如果服务器或后台任务离线，恢复后要补处理已经到期的活动。
-   自动开始/结束的业务时间分别取计划起点/当前有效截止点，每次转换另记实际处理时间；手动提前开始/结束以操作时间为业务时间。
-   离线跨越完整活动时段时，恢复后直接归结为已结束，不开放过期活动、不补时；保留计划起止的业务时间及实际补处理时间，注明系统离线补处理，不声称服务当时可用。
-   即使后台任务尚未更新状态，每次推荐、点赞或取消点赞等写操作仍必须检查当前时间与活动状态。
-   延期必须在当前截止时间之前完成。
-   暂停不会停止倒计时，也不会自动顺延截止时间。
-   管理员可以提前结束活动；提前结束后立即释放剩余时段。
-   活动结束后不可重新开放。要再办活动，必须创建新一期。
-   待开始的活动可以修改计划开始和结束时间，但必须重新检查冲突。
-   草稿可以自由编辑计划时间。
-   进行中或暂停时，不允许修改已经发生的开始时间；可以在截止时间前延期或提前结束。
-   已结束或已取消的活动计划时间锁定。
-   活动名称和主题在草稿、待开始时可编辑；进行中或暂停时允许纠正名称和主题，但必须记录修改前后内容、操作管理员、时间和原因；结束或取消后锁定。
-   尚未开始的活动可以取消，保留原定时间和取消原因，不物理删除。已经开始的活动使用提前结束流程，不使用"取消"状态。

### 6.3 时间冲突规则【已确认】

-   任意时刻最多只能有一个开放参与的活动。
-   正式安排、开始和延期时都必须检查时间冲突。
-   暂停活动仍占用时段。
-   提前结束活动后，按实际结束时间释放时段，可以在原定截止时间之前安排下一期。
-   如果延期会与下一期冲突，拒绝延期；管理员先调整冲突活动时间，再重新延期。
-   时间区间采用左闭右开语义：前一期在 20:00 结束、下一期在 20:00
    开始，不算重叠。
-   自动开始和自动结束任务必须具备幂等性，重复运行不得重复执行破坏性操作。

### 6.4 活动延期审计【已确认】

不单独建立活动延期历史表。`activities.scheduled_end_at`
保存当前有效截止时间，创建、延期、提前结束等操作写入
`admin_audit_logs`，记录操作前后时间、操作管理员、时间和原因。

活动时间更新与审计记录必须在同一事务中完成。

### 6.5 活动作品快照 `activity_works`【已确认】

一部作品首次进入某一期活动时，建立一条 `activity_works` 记录，保存：

-   `activity_id`
-   `work_id`
-   `snapshot_title`
-   `snapshot_author`
-   `snapshot_cover_url`
-   `created_at`（首次进入本期活动的时间）

规则：

-   同一部作品在同一期活动中只有一条有效 `activity_works` 记录。
-   同一期活动的所有推荐者共用一份快照。
-   快照保存书名、作者和封面地址；不保存简介或标签列表。
-   快照创建后，不随文库8更新而改变。
-   作品暂时退出当前活动列表后，保留 `activity_works`
    记录；重新进入时复用原记录和原快照。
-   如果重复作品合并后，同一期活动出现两份快照，保留 `created_at`
    较早的快照作为有效记录；另一份归档，原快照保留在合并变更记录中。
-   封面快照只保存当时的图片地址，不保证远端图片永久可用。是否在服务器保存封面文件仍待技术验证。

### 6.6 活动推荐与撤回【已确认】

-   活动推荐可以不填写理由。
-   活动推荐理由是纯文本，统一换行并去除首尾空白后最多 200 个 Unicode 码点；实时计数，超限禁止提交，不自动截断；前端与服务端按 §7.5 同一口径校验。
-   活动推荐理由匿名展示，不显示提交者昵称或 QQ 号。
-   一部作品在本期活动中只展示一次；不同匿名用户的推荐理由独立保存。
-   用户只能撤回自己的活动推荐。
-   活动进行中可以撤回自己的推荐；撤回后记录使用 `withdrawn_at`
    标记，不物理删除。
-   活动暂停或结束后，普通用户不能撤回、重新推荐或修改理由。
-   用户撤回后可以在活动进行中重新推荐同一部作品。重新推荐创建新记录，旧记录保留撤回时间。
-   同一匿名身份对同一期活动中的同一作品，最多有一条有效推荐记录。
-   撤回活动推荐不自动取消该用户的活动点赞。
-   撤回活动推荐不删除独立的公共推荐理由或公共「+1」。

### 6.7 活动作品何时从当前列表隐藏【已确认】

-   仍有有效推荐：作品留在当前活动列表。
-   没有有效推荐，但有有效活动点赞：作品仍然留在当前活动列表。
-   既没有有效推荐，也没有有效活动点赞：作品从当前活动列表隐藏，但历史记录和
    `activity_works` 快照保留。
-   后续有人重新推荐时，复用原有 `activity_works` 记录和快照。
-   因有效推荐和活动点赞都归零而退出列表后，须在活动进行中重新推荐才能回到列表，不能通过旧链接新增点赞唤回。
-   作品是否出现在当前活动列表，应根据有效推荐、有效点赞、合并状态和隐藏状态判断，不通过删除历史记录实现。

### 6.8 活动点赞【已确认】

-   活动点赞与公共「+1」完全独立。
-   同一匿名身份在同一期活动中对同一作品只能有一个有效点赞。
-   只有活动处于进行中时，普通用户才能新增或取消活动点赞。
-   新增点赞还须校验作品属于本期、当前公开可见且已有本期有效快照；不得通过点赞创建快照，也不得给零贡献已退出本期列表的作品新增点赞。
-   暂停或结束后，普通用户不能新增或取消活动点赞。
-   撤回推荐不自动取消点赞。
-   取消活动点赞只影响该活动的点赞，不删除推荐理由。

### 6.9 活动排序与推荐理由展示【已确认】

活动作品按以下顺序排序：

1.  活动有效点赞数降序。
2.  有效推荐人数降序。
3.  `activity_works.created_at` 升序（先进入活动的作品优先）。

排序动态根据当前有效数据计算，不修改快照。

推荐理由展示：

-   同一作品只展示一次。
-   默认展示最早提交的 2 条有效推荐理由；不足 2 条则展示全部。
-   点击"查看全部推荐理由"后展开所有有效理由。
-   没有有效理由时不显示理由区域。
-   理由按首次提交时间从早到晚排列；修改理由不改变其首次提交时间。
-   同一时间的记录用稳定的记录 ID 等规则确定顺序。
-   已撤回的理由不展示，但保留历史记录。
-   不公开理由作者身份。

### 6.10 时间补处理与历史边界【修订要求】

-   数据库存储统一的 UTC 时间，页面和管理员输入使用 `Asia/Shanghai`；阶段 1 统一时间精度及序列化方式。服务器时间为准，不信任客户端时钟。
-   所有活动写入，包括管理员安排、暂停、恢复、延期、取消和普通用户写入，均在事务内检查有效时间与状态；不得利用调度延迟延长参与窗口。
-   自动状态的业务生效时间与任务实际处理时间分开记录。自动开始/结束分别使用计划起点/有效截止点作为 `started_at`/`ended_at`，每次转换另记实际 `processed_at`；手动提前开始/结束使用操作时间。转换事件须分别保存各自处理时间，不能仅用一个覆盖更新的时间字段代替转换历史；具体表结构在阶段 1 落实。
-   状态转换采用显式矩阵：草稿可安排或取消；待开始可开始或取消；进行中可暂停或结束；暂停可恢复或结束；结束、取消为终态。开始还须满足有效截止时间未到及无时段冲突。待开始活动跨越全时段离线后，允许系统补处理直接归结为已结束，并保留业务起止及处理记录；该路径不开放参与窗口，不是普通开始或管理员重开。
-   提前开始按实际起点重新检查冲突；安排时要求开始早于截止，且不能将已过期时段作为新的可参与活动。相邻活动交界时先归结前一期，再处理下一期；状态检查和占用变更必须原子完成。
-   自动任务的日志标记为系统执行，不伪造管理员 ID；人工操作保留管理员身份。自动补处理必须保留实际处理时间和原因。
-   历史快照仅冻结书名、作者和封面地址，不随来源同步变化；推荐数、点赞数和排名不永久冻结。结束后普通用户不可参与，管理员可通过有审计的纠错、合并/撤销和隐藏/恢复修正历史展示，统计按修正后有效记录重算并提示“已修正”。理由治理按 §7.5 区分文本隐藏和推荐资格失效；该政策不解除活动名称、主题、计划时间锁定，也不放宽合并/撤销安全条件。
-   活动点赞必须校验作品属于本期、当前可见且存在有效 `activity_works`，不得靠点赞创建快照。零贡献退出列表后必须重新推荐才可返回，不能用旧链接新增点赞唤回；取消本人现有点赞仍受进行中状态限制。
-   活动作品排序在既有三项相同时，以有效 `activity_works.id` 升序稳定排序。空白理由不占默认展示两条的名额。

## 7. 管理员后台与安全

### 7.1 管理员账号【已确认】

-   支持多个独立管理员账号。
-   首版所有有效管理员拥有相同的管理权限，不实现复杂角色等级。
-   不开放公开管理员注册。
-   首个管理员通过服务器端配置或初始化命令创建。
-   现有管理员可在后台创建其他管理员。
-   管理员各自登录，不能共用一个固定的公开账号。
-   密码只保存安全哈希，不保存明文。
-   支持停用管理员账号；停用后不能登录或执行管理操作，历史审计记录保留。
-   不允许停用最后一个有效管理员。
-   密码重置或账号停用后，相关旧登录会话必须失效。
-   管理员登录与普通用户匿名 Cookie 完全分开。

### 7.2 管理员可执行的操作【已确认】

-   创建、停用管理员。
-   导入或检查文库8资料。
-   修改作品资料覆盖值，逐字段恢复文库8同步。
-   隐藏和恢复作品。
-   纠正作品别名。
-   处理标签关联和疑似重复标签。
-   创建、安排、修改、延期、暂停、恢复、提前结束或取消活动。
-   确认重复作品并执行合并。
-   在满足安全条件时撤销作品合并。
-   处理必要的错误点赞或内容问题。

### 7.3 审计日志 `admin_audit_logs`【已确认】

重要管理操作成功后必须写入审计日志，至少记录：

-   `id`
-   `admin_id`
-   `action_type`
-   `target_type`
-   `target_id`
-   `before_data`（必要时）
-   `after_data`（必要时）
-   `reason`（适用时）
-   `created_at`

审计数据不得保存匿名令牌、管理员密码或 API
密钥。普通用户不可查看审计日志。管理员不能通过普通管理界面直接修改或删除已有审计记录。管理操作与对应数据更新应使用同一事务，避免操作成功但没有审计记录。

### 7.4 基本安全要求【实现要求】

-   匿名令牌由服务器生成，浏览器只保存令牌；数据库保存令牌哈希，不保存原始令牌。
-   Cookie 使用 `HttpOnly`、适当的 `SameSite`；生产环境 HTTPS 下使用
    `Secure`。
-   管理员登录必须服务端验证，不能信任前端传来的 `admin_id`。
-   管理后台使用独立会话机制。
-   对登录和会触发 DeepSeek API 的接口设置合理的请求频率限制。
-   对 Cookie 身份的写操作采取适当的 CSRF 防护和来源校验。
-   API 密钥通过环境变量或服务器端配置注入，不写入前端、不提交到
    Git、不记录在日志中。
-   所有用户输入都按纯文本处理，不允许把推荐理由当作 HTML 执行。
-   隐藏作品不得通过搜索、别名、活动旧链接或候选接口绕过隐藏规则。
-   已合并作品的旧链接自动跳转主作品；如果主作品隐藏，旧链接不能绕过限制。

### 7.5 输入、治理与并发安全补充【修订要求】

-   匿名身份签发、作品提交、推荐、标签、点赞及搜索接口均设置合理的请求限制；不能只限制登录和 DeepSeek。限流失败不得造成部分写入，具体阈值在部署配置中记录。
-   所有用户提交的作品、活动和关联 ID 都须重新校验归属、可见性及状态，不以“前端不显示按钮”作为权限控制。
-   “最后一个有效管理员”检查与停用必须原子完成，覆盖两名管理员并发相互停用；停用和改密后的旧会话在服务端失效。
-   管理员可隐藏/恢复单条公共或活动理由文本，保留原文审计；不得以编辑匿名用户原文冒充用户修改。文本隐藏本身不取消推荐资格、不减少活动推荐人数；若需取消推荐资格，使用独立、可审计的失效操作。
-   文本治理与推荐资格状态分开保存，用户修改理由不能自动解除治理；历史活动的治理及展示按 §6.10 审计修正政策执行。文本隐藏不应被误作用户撤回或清空，失效贡献不计有效推荐。
-   理由按 Unicode 码点计数，CRLF 等换行归一为 LF、去除首尾空白后判空及校验，最多 200 码点；组合字符不按一个视觉字符合并计算。前后端使用同一组边界样例验证，不能把 JavaScript UTF-16 单元长度当作码点数。
-   书名、别名、活动名称上限分别为 300、300、100 个码点，主题 500、简介 10000；保留原始来源值与输入校验结果，导入超限记录问题，不静默截断。阶段 1 明确各输入字段的规范化流程、共享空白字符口径、分页上限及错误响应；这些实施细节不能改变已确认的码点上限。
-   外部封面 URL 仅接受允许的 HTTP(S) 地址；如启用服务端下载或代理，校验重定向及最终目标、限制大小和超时，拒绝内网及本机地址。下载能力不得作为任意 URL 请求接口。

## 8. 数据库设计基线

### 8.1 数据库选型【已确认】

MVP 使用 **SQLite**。初期用户规模预计不大，SQLite
维护简单，并支持关系、事务、索引和唯一约束。只有出现明确的并发写入或扩展需求时，再评估
PostgreSQL。

实现要求：

-   启用并验证外键约束。
-   为关键关系添加索引和唯一约束。
-   对活动推荐自动收录公共书单、作品合并、合并撤销、活动时间更新等操作使用事务。
-   文库8批量导入分批提交，避免长时间占用 SQLite 写入锁。
-   建立定期数据库备份，并测试恢复流程。
-   如果封面文件下载到服务器，备份策略也要覆盖这些文件。
-   数据库结构变更必须有可重复执行的迁移方案，不在生产环境手工随意改表。

### 8.2 核心逻辑表清单

首版逻辑数据表：

1.  `works`：作品资料、公共书单收录、隐藏和合并状态。
2.  `work_aliases`：已确认的作品别名。
3.  `tags`：文库8标准标签定义。
4.  `work_tags`：作品与标签的来源关联。
5.  `anonymous_clients`：匿名浏览器身份。
6.  `recommendations`：公共推荐理由和活动推荐。
7.  `votes`：公共「+1」与活动点赞。
8.  `activities`：月度活动信息与状态。
9.  `activity_works`：每部作品在每期活动中的记录和展示快照。
10. `work_merge_operations`：每次作品合并/撤销的整体记录。
11. `work_merge_changes`：合并涉及的逐项数据变更。
12. `admins`：独立管理员账号。
13. `admin_audit_logs`：管理员操作审计。

管理员会话可以使用安全的服务端会话实现；是否增加独立 `admin_sessions`
表由实现方案决定，不属于已确认的产品规则。

上述为核心逻辑表，不是禁止新增表的封闭清单。阶段 1 还须落实字段覆盖状态、标签来源映射与纠错标记、请求幂等、系统状态转换记录，以及合并后变更检测所需的版本/删除标记或事件记录。历史统计按有效记录重算，不要求永久冻结排名的结果快照；须保留历史修正的审计及展示标记。待核查公开状态、作品级标签禁止、理由文本治理与独立推荐资格失效结构从阶段 1 落实，不能等到阶段 6 才补采已经丢失的变更历史。

### 8.6 `work_tags` 作品标签关联表字段方向

  `work_id`                   作品 ID

### 8.7 `anonymous_clients` 匿名身份表字段方向

  `token_hash`     匿名令牌哈希，唯一
  `created_at`     创建时间
  `last_seen_at`   最近访问时间
  `revoked_at`     身份失效时间，可为空

匿名身份记录及其贡献长期保留；清除浏览器数据只会丢失客户端令牌，不会自动删除服务端记录。Cookie 的精确有效期、续期与重置页面尚待实现前确定。主动重置不转移旧记录权限，不删除历史贡献。

### 8.8 `recommendations` 推荐表字段方向

公共推荐与活动推荐可以共用一张表，以范围字段区分。

  字段                              用途
  --------------------------------- ------------------------------------
  `id`                              推荐记录 ID
  `work_id`                         作品 ID
  `anonymous_client_id`             提交者匿名身份
  `scope_type`                      `public` 或 `activity`
  `activity_id`                     活动推荐所属活动；公共推荐为空
  `reason`                          推荐理由；公共有效记录须非空，活动记录允许为空；规范化后最多 200 码点
  `created_at`                      首次提交时间
  `updated_at`                      最后修改时间
  `withdrawn_at`                    活动推荐撤回时间，可为空
  `archived_at`                     合并冲突等情况下的归档时间，可为空
  `merged_into_recommendation_id`   被去重时指向有效记录，可为空

关键约束：

-   公共推荐的 `activity_id` 必须为空；活动推荐必须关联活动。
-   公共推荐：同一匿名身份对同一作品最多一条有效公共理由记录。
-   公共空理由提交只确保作品收录，不新建空公共推荐记录；清空已有公共理由删除对应记录，但保留作品收录状态，不能因此撤销公共「+1」或活动记录。
-   活动推荐：同一匿名身份对同一期活动中的同一作品最多一条有效记录。
-   活动空理由仍创建有效推荐记录并计人数。活动理由复制到公共范围须满足 §2.3 的主动勾选、非空及无已有有效公共理由条件，并与活动提交同事务完成。
-   撤回的活动推荐保留历史；重新推荐创建新记录。
-   合并冲突时，公共理由以 `updated_at`
    较新的记录为有效记录，另一条归档；若时间完全相同，暂停自动选择并交管理员决定。
-   同一匿名身份的活动推荐冲突仅在同一期内处理，保留 `updated_at` 较新的有效记录，另一条归档；时间相同由管理员选择，未裁决不提交整次合并。不同活动之间互不覆盖。
-   空白理由不显示。

理由文本治理状态与推荐资格状态独立于 `withdrawn_at`、`archived_at`：管理员隐藏文本时保留原文审计、不取消推荐人数；独立资格失效后不计有效推荐；用户编辑不得解除治理。公共理由清空仍按 §2.2 删除本人记录并保留必要删除事件，不因新增治理结构变成自动保留所有已删除正文。具体字段及审计存储在阶段 1 定稿。

### 8.9 `votes` 点赞表字段方向

  字段                    用途
  ----------------------- ----------------------------------
  `id`                    点赞记录 ID
  `work_id`               作品 ID
  `anonymous_client_id`   操作者匿名身份
  `scope_type`            `public` 或 `activity`
  `activity_id`           活动点赞所属活动；公共「+1」为空
  `created_at`            点赞时间

关键约束：

-   公共「+1」按 `work_id + anonymous_client_id` 防止重复有效记录。
-   活动点赞按 `activity_id + work_id + anonymous_client_id`
    防止重复有效记录。
-   取消点赞移除当前有效记录；重新点赞可建立新有效记录。
-   合并作品时出现的重复点赞应在合并变更明细中保存必要快照，以支持追溯和有条件撤销。

### 8.10 `activities` 活动表字段方向

  字段                 用途
  -------------------- --------------------------------------------
  `id`                 活动 ID
  `title`              活动名称
  `theme`              活动主题，可为空
  `start_at`           计划开始时间
  `scheduled_end_at`   当前有效计划截止时间
  `started_at`         业务开始生效时间，可为空；自动取计划起点，手动提前开始取操作时间
  `status`             草稿、待开始、进行中、暂停、已结束、已取消
  `ended_at`           业务结束生效时间，可为空；自动取有效截止点，手动提前结束取操作时间
  `end_reason`         结束原因
  `cancelled_at`       取消时间，可为空
  `cancel_reason`      取消原因，可为空
  `created_by`         创建管理员 ID
  `created_at`         创建时间
  `updated_at`         最近更新时间

不把推荐数或点赞数作为可独立修改的字段保存；页面根据有效记录统计，避免冗余计数不一致。

每次状态转换另存实际处理时间 `processed_at`、系统/管理员操作者、原因及业务生效时间；跨全时段离线补处理保留业务起止和实际处理记录，不生成可参与的临时进行中状态。转换历史具体结构在阶段 1 定稿。历史修正记录须支持审计追溯及往期“已修正”提示，不能把来源资料同步误算成历史统计修正。

### 8.11 `activity_works` 活动作品表字段方向

审计日志不得包含密码、匿名令牌原文或 API 密钥。

## 9. 重复作品合并与安全撤销

### 9.1 何时允许合并【已确认】

-   相同且可信的文库8作品 ID 可作为同一标准作品的证据，但正式库非空 ID 唯一，正常情况下不会同时存在两条此类记录。该判断用于导入暂存、历史异常修复或尚未写入的身份确认，不以违反唯一约束作为合并前提。
-   如果只有一条记录有有效文库8 ID，优先保留该记录作为主作品。
-   两条记录都没有文库8 ID 时，由管理员选择主作品。
-   两条记录对应不同的文库8作品 ID 时，禁止直接合并，必须进一步核查。
-   书名相似、作者相同、译名相近或 AI 建议都不能单独作为自动合并依据。
-   合并前必须展示两条作品资料及相关记录，让管理员明确确认。

### 9.2 合并后的主记录与旧链接【已确认】

-   保留主作品的本地 ID。
-   被合并作品不物理删除，标记为已合并并通过 `merged_into_work_id`
    指向主作品。
-   访问旧作品链接时自动跳转到主作品详情页。
-   如果主作品被隐藏，旧链接不能绕过隐藏限制。
-   合并操作使用数据库事务，并写入
    `work_merge_operations`、`work_merge_changes` 和
    `admin_audit_logs`。

### 9.3 各类关联数据的合并规则【已确认】

**推荐理由**

-   同一匿名身份对同一合并后作品存在两条公共理由时，保留 `updated_at`
    较新的理由作为有效理由，另一条归档。
-   如果修改时间完全相同，暂停自动选择，由管理员决定。
-   同一匿名身份的活动推荐仅在同一期活动内比较，保留更新时间较新的有效记录，另一条归档；同时间由管理员选择，未选择则整次不合并。不同活动的理由互相独立。
-   公共理由与活动理由互不覆盖。

**标签**

-   迁移两条作品的所有有效标签关联，保留来源和操作者。
-   同一标签在页面只显示一次。
-   同一来源、同一操作者产生的重复有效关联只保留一条，其余归档。
-   普通用户仍然只能撤销自己的关联，不能撤销其他人的关联或文库8来源关联。

**点赞**

-   公共「+1」：同一匿名身份对合并后的作品只计一次。
-   活动点赞：同一匿名身份对同一期活动中的合并后作品只计一次。
-   不同活动的点赞互不影响。
-   不同匿名身份的有效点赞全部保留。
-   被去重的记录不参与统计，但在合并变更记录中保留必要快照。

**别名**

-   将别名迁移到主作品。
-   同一作品内完全相同的别名只保留一条有效关联。
-   同一个别名可以对应不同作品；不自动合并其他作品。
-   保留原始别名和必要来源信息。

**活动作品快照**

-   如果同一期活动中出现两条重复作品的 `activity_works` 记录，以
    `created_at` 较早的快照为准。
-   另一条归档，快照内容保留在合并变更明细中。
-   推荐理由和点赞仍按上述规则迁移和去重。

**作品资料与隐藏状态**

-   有文库8 ID 的记录优先作为主作品。
-   管理员手动覆盖必须保留。
-   如果任一重复记录已隐藏，合并后先保持隐藏，只有管理员明确恢复才能重新公开。
-   首次公共收录时间取两个记录中较早的有效时间。
-   原始提交书名保留供追溯。

**合并预览与冲突裁决补充：**

-   公共理由与同一用户同一期活动推荐均按修改时间选择有效记录，同时间由管理员选择；双方同一字段的管理员覆盖值不同时，须逐字段明确选择，未选择则整次不合并。所有原值保留在变更明细中，不能因选择主作品而静默覆盖另一方。覆盖状态含主动空值时也须按 §4.5 语义比较。
-   活动快照创建时间相同，使用较小记录 ID 作为稳定裁决；不修改保留快照的内容。已结束活动允许有审计的合并/安全撤销，统计按处理后有效记录重算并提示“已修正”，仍须满足全部冲突与撤销保护。
-   不同文库8 ID 禁止直接合并，包括管理员手动提交接口。若来源绑定错误，先独立核验并审计纠正 ID，再按新身份关系进入合并预览，不得自动清空一个 ID 来绕过禁令。
-   预览不执行部分迁移。提交时在事务中复核记录版本、权限、目标身份、隐藏状态及冲突选择；预览后数据变化时重新预览，未决冲突导致整次不提交。
-   主作品必须解析到有效根记录；禁止自合并和循环。旧链接可沿链解析至最终主作品，并在最终主作品处检查隐藏权限。

### 9.4 安全撤销合并【已确认】

-   每次合并生成独立操作记录和逐项变更明细。
-   记录合并前后的作品 ID、关联迁移、去重、归档和必要快照。
-   合并后的新增、修改、删除、撤回、取消、同步、纠错及后续合并都必须可检测；仅保存合并时的前后快照不足以实现安全撤销。
-   管理员申请撤销时，系统逐项检查新增数据归属，以及原有受影响记录是否仍与合并后版本一致。
-   若不存在歧义，才执行安全撤销。
-   若新推荐、点赞、标签、别名或活动关联无法安全拆回，暂停自动撤销并交管理员核查。
-   合并和撤销都使用事务，必须整体成功或整体回滚。
-   撤销本身也记录在审计日志中。
-   保留旧记录不等于可以无条件撤销；不得覆盖合并后新增的数据。

-   用户合并后取消的点赞、清空的理由或撤回的关联不得因恢复旧快照而复活；修改过的内容不得被旧值覆盖。删除事件通过墓碑、变更记录或等效持久机制识别，不要求保留已删除理由的正文。
-   撤销不得解除合并后新增的隐藏或治理限制，也不得悄悄覆盖管理员覆盖值及来源更新。
-   存在依赖该合并的后续合并时，先撤销后续依赖；无法安全撤销依赖则拒绝当前自动撤销。任何数据归属或状态有歧义时整体停止，不部分撤销。
-   新增数据即使能明确保留在主作品，也必须验证拆分后的唯一约束、活动归属及历史政策。没有归属证据不能凭时间猜测。
-   撤销预览与最终执行之间使用版本复核；冲突检测、恢复、唯一约束校验和审计在同一事务中完成。人工核查只能提出新的明确处理方案，不能跳过保护强制回放快照。

## 10. 数据库约束与一致性要求

以下是实现必须落实的约束方向。具体 SQLite DDL 由 Codex
在检查项目结构后确定。

### 10.1 唯一性与外键

-   `works.wenku8_book_id` 非空时唯一。
-   作品书名不设置全局唯一约束。
-   匿名令牌哈希唯一。
-   管理员用户名唯一。
-   公共推荐、活动推荐、公共点赞、活动点赞、标签关联和活动作品均需要防止重复有效记录。
-   外键约束应启用并覆盖核心关联。
-   对可能存在归档历史的关联，优先使用部分唯一索引或等效约束保证"有效记录唯一、历史记录可保留"。

-   推荐与点赞均校验 `scope_type` 与 `activity_id` 的组合；活动关联须对应同一期的有效作品关系，不能引用其他活动的快照。合并归档记录保留历史，但禁止新操作写入归档目标。
-   不使用一个含可空 `activity_id` 的组合唯一索引代替全部范围约束；公共和活动范围分别建立适用的有效记录约束。标签按来源类型分别校验操作者及唯一性，避免可空操作者造成重复来源关联。
-   阶段 1 为每类关联定义唯一的“有效”判定，统一供查询、计数、权限及部分唯一索引使用；归档、撤回、治理及隐藏对有效性的不同影响不得各接口自行解释。

### 10.2 事务要求

以下操作必须在事务内完成：

-   活动推荐与公共书单自动收录。
-   创建新作品前的重复检查与记录创建。
-   活动时间修改与审计记录。
-   作品合并、关联迁移、去重与审计记录。
-   作品合并撤销及其变更记录。
-   管理员创建/停用等状态修改与审计记录。

### 10.3 统计要求

-   点赞数只统计有效点赞。
-   推荐人数只统计有效推荐记录。
-   已撤回推荐不展示、不计数。
-   已归档或已合并的关联不重复计数。
-   活动作品数不直接保存为可独立修改的计数器。
-   任何页面缓存的统计都必须可重算，不能作为唯一真实来源。

### 10.4 SQLite 实现注意

-   开启外键约束。
-   合理设置事务和超时，避免批量导入长期占用写锁。
-   使用迁移脚本维护 schema 版本。
-   重要操作需有并发测试，尤其是重复提交、活动时间冲突、点赞和作品合并。
-   定期备份数据库，并进行至少一次实际恢复演练。

### 12.1 开发与部署基线【已确认方向】

-   网站部署到用户租用的服务器。本地开发和测试，通过 Git 管理版本，将代码推送到 GitHub 私有仓库，由服务器拉取已验证的版本部署。

-   Git 保存源码、必要测试样例、依赖锁定文件、迁移、部署脚本和无真实密钥的配置示例。首次提交前检查忽略规则与暂存清单，避免上传本地虚拟环境、缓存、浏览器会话资料、真实配置、数据库、日志及大批运行产物；必要的历史验证证据在本地保留，不因忽略而删除。
