## 5. 文库8路线与复用缺口

历史在线证据：`online_search_20261018/test_report.md`（直达详情 4151/2951、四候选列表）、`selected_detail_20261018/test_report.md`（选择 3219 并核对详情）、`logging_online_review_20261018/test_report.md`（客户端观测到三个范围内独立导航实例）。本轮重新运行的是这些保存样本的离线回归，不冒充新的真实浏览器采集。

历史列表的 3219/2951 长标题截断，详情能补全；列表标题只供候选展示。仅有三个独立作品的详情样本，不能推导全站兼容性、总量、存储容量或失败率。

复用时需要增加独立的生产适配层，保留原型当前验收语义：

1. **字段状态**：旧详情解析器把空值和缺失大多归为 parse_error，CLI 又要求作者、字数、封面、标签等全非空。生产导入按可信 ID 和详情标准书名验证身份，其他字段按有效值/明确空/未获取/解析失败分别处理，失败值不能清空旧值；身份失败隔离该条。
2. **标签完整性与身份**：当前输出只有标签名称，无原始标签 ID；保存的 3219 标签区域为纯文本。只能证明当前样本无 ID，不能证明站点所有入口都无 ID。完整标签集合状态、原始身份映射及管理员抑制标记须另建，不能用空数组撤销全部来源关联。
3. **依赖方向**：当前 CLI 动态加载历史三词脚本，以取得快照及工具。将来先用回归测试固定行为，再抽出共享快照/解析模块，网站不能执行历史脚本 main，也不能把调试浏览器作为公网请求的同步后端。
4. **安全与流量**：记录器只覆盖文库8导航；资源、其他 Context 和监听前流量不在预算内。HTML 快照只作受控证据，不进入前端直接渲染。封面样本为 HTTP URL，HTTPS 页展示与远端可用性未测；未定存储政策前使用占位图降级，不承诺封面可显示。

推荐阶段 2 的有限验证：优先复用这三部作品既有详情作为离线固定样本；获得服务器条件后，在服务器一次一个请求检查访问政策及指定详情，遇登录、验证码、429/403 或未知页即停止。初始候选节奏为单并发、每次至少间隔 10 秒且不自动重试，**这是保守实验参数，不是站点允许频率的事实**。任何新增搜索预算须写清搜索 POST、重定向和详情导航，而非只统计点击。

服务器不可直接访问时，保留人工辅助本地 Chrome → 仅元数据 JSON → 服务器验证导入的备选路线；不转移浏览器会话或要求服务器绕过限制。生产导入应有暂存、版本、校验摘要、每条结果、断点、幂等与失败隔离；目前没有实现。更大范围采集仍须在小样本验收后另行确认。

## 6. DeepSeek：文档能力与账号实测分开

2026-10-18 查询的[官方 Search / Fetch 文档](https://api-docs.deepseek.com/guides/search/)列出独立 `POST /v1/tools/search`、`POST /v1/tools/fetch`，使用 Bearer 认证。因此联网检索存在独立接入路线，不能仅凭普通模型响应宣称发生了检索。[官方模型及价格页](https://api-docs.deepseek.com/quick_start/pricing/)当前列出 `deepseek-flash` 与 `deepseek-v4-pro`；本项目没有模型锁定或账号实调证据，本文不承诺其额度、价格或准确率。

本轮部分首页/Tool Calls 文档请求超时；Search 指南及价格页可读取。缺项目配置密钥、端点与模型，未发送认证请求，故以下全部待验证：模型调用、结构化输出稳定性、独立搜索账号权限、延迟、实际费用、空结果、429/超时及站点覆盖率。

建议先以本地书目为检索范围，让模型纠错与排序。只接受本地候选 ID，服务端复核隐藏与合并状态；候选仍由用户确认，AI 不生成标签、不自动合并。外部搜索只作可选适配器，搜索结果不作为可信来源身份；启用前单独验证和配置预算。模型 ID、base URL、密钥、调用超时均走服务端配置；不把参数建议当作已测性能。

阶段 3 最小实调方案：固定输入集合覆盖正确标题、错字、缺字、别名、歧义、无候选；保存脱敏输入、候选 ID、模型 ID、usage、耗时与错误分类；精确命中零调用；模拟和实测分别记录。外部接口未就绪不阻塞本地搜索与直接提交。

按该预算，推荐先评估单个网站进程、单实例轻量定时任务与 SQLite，不预设 Redis/Celery、多个应用副本或服务器内常驻 Chrome。模板前端无需大型构建链；若选容器或出现依赖编译，优先在匹配服务器架构的本地/CI 环境构建，分别测构建峰值与稳态运行资源。初次上线记录 RSS、系统可用内存/swap、CPU、磁盘/WAL/日志增长、写锁与响应延迟，再依据结果调整，不凭规格要求升级，也不声称容量测试通过。40 GiB 还需为既有服务、系统更新、多个发布版本和备份保留空间；同机备份不能代替独立故障域的备份。

仍缺 CPU 架构、实际内核/运行时、已有服务与端口、实际可用内存/swap、磁盘文件系统与持久卷、Docker、域名/DNS、反向代理/HTTPS、GitHub/依赖源/DeepSeek/文库8连通性、流量额度及私有仓库地址。没有复制公网/私网 IP、实例 ID 或连接凭据。

首次 Git 初始化前，根级忽略应覆盖 `.venv/`、`__pycache__/`、所有浏览器 profile、真实 `.env`/私钥、SQLite 及 WAL/SHM、日志、备份、运行输出与审查 sandbox；明确保留 `.env.example`、迁移、锁文件和最小去敏样本。现有忽略只在 `tests/wenku8_browser/.gitignore`，范围不足。暂存采用明确路径，并用 `git status`、`git diff --cached --stat`、暂存文件清单及密钥检查复核；不能因仓库私有就上传会话资料。本地证据保留，不通过删除历史来精简仓库。本轮未执行首次暂存，故没有“暂存审查通过”的结论。

Ubuntu 服务器可采用 `/srv/shared-books/releases/<commit>/` 存代码，`/var/lib/shared-books/` 存 SQLite/必要封面，`/var/log/shared-books/` 存日志，独立备份目录与受限 `/etc/shared-books/` 配置；目录、权限和磁盘类型仍须实测。WAL 数据不得放网络共享盘。服务器拉仓库用专用只读凭据，不使用开发者个人写权限 token。

若已有 Docker 和本地持久卷，候选为固定镜像摘要/指定提交构建 + 单网站服务 + 单调度入口；否则候选为独立 venv + WSGI 服务 + systemd + 现有反向代理。根据 Ubuntu 镜像，systemd 路线具备评估基础，但尚未核实实际服务配置。二者都不使用临时文件系统保存数据库，不在多个主机上共享 SQLite，不以 `runserver` 作为生产入口。

手动发布脚本验收顺序建议：

1. 获得部署互斥锁；核对目标标签解析到预期提交、工作目录、配置、空间、运行时与持久目录权限。
2. 在新 release 安装锁定依赖/构建静态资源并完成无写入预检，不提前切换在线代码。
3. 进入维护模式，停止网站及调度/导入写入，排空在途事务；用 SQLite backup API 生成迁移前一致性备份，记录提交、schema 版本和校验。封面纳入备份时同步保留清单。
4. 新版本执行迁移；失败立即停止，保留备份和日志，不能继续启动不兼容代码。
5. 切换 release，启动服务，检查进程、HTTP、配置与数据库 schema/外键状态，再恢复流量与单实例调度。
6. 健康检查失败时按迁移兼容性选择回退；旧代码只在 schema 明确兼容时启动。数据库恢复单独决策，说明可能丢失备份后贡献，不能自动覆盖线上库来掩盖问题。

以上没有执行；部署脚本、域名、TLS、真实持久卷与全站备份恢复均为阶段 7 验收。备份频率/RPO/RTO 和日志保留仍待用户环境与可接受损失范围明确，不虚构容量或成本。
